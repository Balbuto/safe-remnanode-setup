# Переход с v1.1.0 на `1.1.0+hardening.13`

Это локальная ревизия на основе коммита `274d84d`. В `.11` убрано ложное сообщение об отсутствии старого `docker-compose.yml` на чистом сервере; настройки транспортов не менялись. Не запускайте её впервые на рабочем сервере: проверьте на снапшоте или отдельной VM с той же конфигурацией. Откройте внеполосную консоль и сохраните `/opt/remnanode`, активные правила firewall, конфигурацию Certbot и установленные CLI-копии. Не публикуйте резервную копию `.env`: в ней ключ ноды.

1. Проверьте локальный файл и выполните `sudo bash ./safe-remnanode-setup.sh install-cli`. Эта команда заменяет основную локальную копию, но не обновляет контейнеры и не перезаписывает занятые сторонними alias. Установленный systemd-экземпляр RKN-Watcher в `/opt/rkn-watcher` обновляется отдельно его штатной установкой/обновлением.
2. В `.12` только первый запуск установки ноды может включить неактивный UFW: определяется и проверяется фактический порт SSH, сохраняется разрешение для него, затем включается UFW. На рабочем деплое и в командах `node-transports`, `node-logs`, `install-cli` UFW автоматически не включается. Системная политика не меняется; существующие правила не удаляются. Если установщик остановился на проверке UFW, откройте консоль провайдера, проверьте порт SSH и действующие правила. При частичной ошибке некоторые новые правила могут остаться: сверяйтесь с журналом и статусом UFW. При удалении ноды сетевые правила сохраняются.
3. При следующем применении Compose webroot переключится на `/opt/remnanode/www`. Старый `/var/www/html` не переносится и не удаляется. Кастомный Xray из старого Compose сохраняется как `legacy`, пока вы явно не выберете другую версию. Для проверки TLS рекомендуется отдельный тестовый домен. Standalone требует свободного TCP/80; порт не освобождается остановкой сервисов. Ветка Gcore требует предварительно установленный совместимый Certbot-плагин.
4. Для нового TLS выпуска создаётся собственный lineage `safe-remnanode-<домен>`. Старые сертификаты и старый `copy-remnanode-certs.sh` автоматически не удаляются: это сохраняет продление для работающей старой конфигурации при неудачной миграции. После успешной миграции убедитесь, что используется новый lineage и новый hook, затем вручную выведите из эксплуатации старый hook, если он больше не нужен. Оригиналы ключей Certbot при удалении ноды не трогаются.

### Обновление Xray и темы на существующей ноде

`install-cli` обновляет только сам инструмент. Чтобы обновить движок, откройте `sudo remnanode` → пункт 3 → «Последний стабильный релиз». Этот релиз монтируется контейнеру как `/usr/local/bin/xray`; отдельную настройку `core` в панели Remnawave, если она задана, проверьте отдельно: панель может выбирать другой бинарник. При сбое получения или проверки архива текущий деплой не меняется.

Меню ноды → пункт 6 позволяет выбрать встроенный HTML-шаблон. На установке с отдельным webroot он применяется без перезапуска. Для наследуемой установки, которая всё ещё монтирует `/var/www/html`, шаблон сохраняется локально и станет виден после следующего применения Compose.

### Выбор SNI для VLESS-Reality (.13)

При новой установке выберите пункт **1 — VLESS-Reality (с выбором SNI)**. Укажите DNS-имя, разрешённое в `serverNames` Reality-inbound. Установщик сохраняет его в `.decoy_domain` для последующей генерации nginx. `install-cli` не меняет SNI существующей ноды и не применяет Compose. Профиль Remnawave и настройки клиентов остаются под вашим управлением.

### Повторная установка и UFW

Версия `.5` проверяет правила через `ufw --dry-run` и не применяет те, которые UFW помечает как уже существующие для всех нужных семейств адресов. Список `.xray_ports` нормализуется: одинаковые записи и диапазоны из одного порта сводятся к одной записи, базовый 443 повторно не добавляется. Старые правила не удаляются автоматически. В `sudo ufw status numbered` записи с `(v6)` и без него, а также TCP и UDP, не являются дублями. Пересекающиеся диапазоны — разные правила и автоматически не сворачиваются.

### Файловые логи и пути к TLS-сертификату (.6)

На новой установке бинды и `logrotate` подключаются автоматически. На деплое, созданном этим установщиком, выполните из распакованного каталога:

```bash
sudo bash ./safe-remnanode-setup.sh install-cli
sudo safe-remnanode-setup node-logs
```

`node-logs` не повторяет выпуск сертификата или настройку UFW. Он сохраняет закрытую резервную копию `.env`, Compose и `nginx.conf`, затем заново генерирует конфиги и применяет их. Контейнеры с изменёнными монтированиями пересоздаются; ручные правки надо сверить с резервной копией. Старые файлы журналов не удаляются. Если на хосте уже есть собственная ротация для этих файлов, уберите дублирование вручную. Для файлов трафика Xray укажите пути в [профиле панели](USER_GUIDE.md#пункт-7--диагностика-и-логи).

Штатный образ nginx — `nginx:1.31`. Перед обновлением Compose для TLS/xHTTP скрипт проверяет пару сертификат/ключ и имя ноды. Файлы доступны в контейнерах по пути `/etc/letsencrypt/live/<домен-ноды>/{fullchain.pem,privkey.pem}`. Начиная с `.8`, для новых wildcard-сертификатов добавляется и путь по зоне. Для уже выпущенной пары можно сохранить этот путь командой `sudo safe-remnanode-setup node-logs ns8.pw`. Например, для `spb.ns8.pw` оба пути доступны: `/etc/letsencrypt/live/spb.ns8.pw/` и `/etc/letsencrypt/live/ns8.pw/`.

На хосте файлы не перемещаются: оба контейнерных пути указывают на одну пару в `/opt/remnanode/certs/managed/<домен-ноды>/`. `/etc/xray/certs` также сохраняется. В TLS/xHTTP nginx не завершает TLS на Unix-сокете. Если nginx завершает TLS в режиме Reality, он использует сертификат только при совпадении с настроенным `server_name`.

### Три транспорта на одной ноде (.10)

У одной записи **Node** может быть только один активный **Config Profile**. Включите в этом профиле три inbound: VLESS+TLS, VLESS+xHTTP+TLS и Hy2. Запишите их фактические порты из панели. Установщик не меняет конфигурацию Xray в панели, сертификаты и назначения хостов при добавлении портов.

На действующей ноде с ручными правками Compose или nginx не запускайте повторную установку или `node-logs` только ради портов. После обновления CLI используйте команды (замените имена переменных на фактические значения):

```bash
sudo safe-remnanode-setup node-transports "$VLESS_TLS_TCP" "$VLESS_XHTTP_PORT_PROTO" "$HY2_UDP"
sudo safe-remnanode-setup node-check-ports
```

`node-transports` проверяет и при необходимости добавляет правило управления от IP панели и три разрешения: VLESS+TLS по TCP, xHTTP по указанному TCP или UDP и Hy2 по UDP. Для xHTTP поверх HTTP/3 обязателен суффикс `/udp` (например `1500/udp`); номер без суффикса означает TCP и сохраняет совместимость с `.9`. Он сохраняет список в `/opt/remnanode/.transport_ports` без изменения режима, Compose, nginx, TLS и без перезапуска контейнеров. Список хранится независимо от `.protocol`, поэтому остаётся доступен после операций, которые не меняют UFW. Прежние правила остаются: перечитайте `sudo ufw status numbered` и уберите устаревшие разрешения только после проверки доступа. `node-check-ports` проверяет локальные сокеты Xray (`ss`), но не заменяет внешнюю проверку TLS, обмена xHTTP и QUIC-подключения Hy2.

Для новой установки выберите режим **4**. При использовании TLS-сертификата зоны `ns8.pw` в соответствующих TLS-настройках панели укажите пути `/etc/letsencrypt/live/ns8.pw/fullchain.pem` и `/etc/letsencrypt/live/ns8.pw/privkey.pem`. При нескольких TLS-именах сертификат должен покрывать каждое из них. Для существующего nginx, который сам завершает TLS на Unix-сокете, сохраняйте его текущий конфиг: штатная регенерация для нового режима создаёт сокет без TLS.

## Границы этой ревизии

- Откат Compose при ошибке применения — попытка вернуть файлы и повторно поднять старую конфигурацию. Он не откатывает внешние изменения, включая правила UFW, полученные сертификаты и системные пакеты, и не гарантирует нулевой простой. `up --wait` проверяет состояние контейнеров и доступные healthcheck, а не подключение панели к ноде. Удаление рабочего деплоя, обновление и продление не следует запускать параллельно.
- Для кастомного Xray архив проверяется по SHA256 из `.dgst` того же upstream-релиза. Это проверка целостности, а не независимая подпись. Digest-пиннинг Docker-образов и транзакционная переработка внутренней политики RKN-Watcher остаются отдельно. RKN-фильтрация в этой ревизии не расширена на IPv6.
- Сетевой профиль ноды больше не включается по умолчанию и не удаляет конфиг базового профиля. Если включаете его, проверьте эффективные значения до и после перезагрузки: файлы администратора могут иметь более высокий приоритет.

## Проверка без VPS

```bash
bash -n safe-remnanode-setup.sh
shellcheck -x safe-remnanode-setup.sh tests/smoke.sh
bash tests/smoke.sh
```

Smoke-тесты подменяют Docker, UFW и Certbot, не требуют root и не меняют сервер. Перед эксплуатацией отдельно проверьте реальный Compose, выпуск и продление TLS, установку и обновление через systemd, доступ панели и ручное удаление оставшихся правил.

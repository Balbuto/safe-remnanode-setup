## 1. Что понадобится перед установкой

### Требования к серверу

| Требование | Значение |
|---|---|
| **ОС** | Ubuntu 24.04 LTS (рекомендуется) или Debian 11/12+ |
| **Права** | root (или пользователь с sudo) |
| **Архитектура** | amd64 (x86_64) или arm64 |
| **Минимум ресурсов** | 1 CPU, 1 ГБ RAM, 10 ГБ диска (для ноды лучше 2 ГБ RAM) |
| **Сеть** | Открытые порты 80/TCP, 443/TCP+UDP (для ноды); остальное скрипт настроит сам |
| **DNS** | A-запись домена ноды → IP сервера (если планируете VLESS+TLS или xHTTP) |

### Что нужно подготовить заранее

- **IP-адрес панели Remnawave** — адрес вашего основного сервера с панелью (не этого!)
- **Домен ноды** — например `node.example.com` (можно поддомен)
- **Secret key ноды** — выдаётся в панели Remnawave (раздел Nodes → создать ноду). Выглядит как длинная строка
- **Email** — для выпуска SSL-сертификатов Let's Encrypt (если нужен TLS)
- Для SSL через DNS-API: **Cloudflare API Token** или **Gcore API Token**

> ⚠️ **Важно:** скрипт меняет системные настройки (сетевой стек, файрвол, sysctl). Рекомендуется устанавливать на **свежий сервер** или сервер, на котором нет других критичных сервисов.

## 2. Установка скрипта

### Обычная установка на VPS

Для установки предназначен **однофайловый релиз** `safe-remnanode-setup.sh`. После публикации этой ревизии в `main` команда `wget` ниже скачает именно его: модули установщика и закреплённый RKN Watcher уже встроены. Отдельно переносить на сервер `lib/`, `vendor/`, Python-сборщик или модульный загрузчик не нужно.

```bash
wget -O safe-remnanode-setup.sh https://raw.githubusercontent.com/Balbuto/safe-remnanode-setup/main/safe-remnanode-setup.sh
```

Проверьте загруженный файл, затем откройте меню:

```bash
chmod +x safe-remnanode-setup.sh
sudo ./safe-remnanode-setup.sh
```

Для прямого запуска установки ноды используйте `sudo ./safe-remnanode-setup.sh node`. Если вы скачали полный ZIP репозитория, распакуйте его и запускайте `safe-remnanode-setup.sh` из корня проекта.

### Если вы разрабатываете установщик

Редактируйте исходники в `lib/` и `vendor/rkn-watcher/`, затем пересобирайте релиз и проверяйте его актуальность:

```bash
python3 tools/build_standalone.py
python3 tools/build_standalone.py --check
```

`safe-remnanode-setup-modular.sh` запускается только из полного дерева исходников и предназначен для разработки/тестов. Для обычной установки и обновления CLI используйте однофайловый `safe-remnanode-setup.sh`, а не модульный загрузчик.

На действующем сервере команда `sudo bash ./safe-remnanode-setup.sh install-cli` обновляет локальную копию и создаёт команды `remnanode` и `rkn-watcher`, не перезаписывая занятые сторонними командами пути. Она не переустанавливает ноду и не меняет RKN Watcher. На чистом сервере неактивный UFW может быть включён установщиком после добавления разрешения для SSH. При обновлении действующей ноды UFW должен быть активен заранее. Перед обновлением см. [заметки миграции](MIGRATION.md).

## 5. Модуль A: настройка сервера

Пункт 2 главного меню. Проводит базовую настройку **по шагам с вопросами** — вы выбираете, что делать:

```
БАЗОВАЯ НАСТРОЙКА СЕРВЕРА - выберите шаги

1. Обновить систему? [Y/n]
2. Установить базовый софт (mc, net-tools, ncdu, iftop, curl, wget, git)? [Y/n]
3. Установить Docker (apt + GPG)? [Y/n]
4. Включить BBR + Cake qdisc? [Y/n]
5. Hardening профиль: [s]afe / [h]ighload / [a]uto / [n]one
6. Установить irqbalance? [Y/n]
```

| Шаг | Что делает | Когда нужно |
|---|---|---|
| 1. Обновление | `apt update` + `upgrade` + `dist-upgrade` | Всегда при первом запуске |
| 2. Базовый софт | mc, net-tools, ncdu, iftop, curl, wget, git | Удобно для администрирования |
| 3. Docker | Официальный репозиторий docker.com, GPG-ключ, compose-плагин | Обязательно для ноды |
| 4. BBR + Cake | Включает TCP BBR и qdisc cake (файл `/etc/sysctl.d/99-bbr-cake.conf`) | Рекомендуется для VPN-нагрузки |
| 5. Профиль ядра | **SAFE** — консервативный; **HIGHLOAD** — для мощных серверов (nofile 1M+, conntrack 2M); **AUTO** — выбор по RAM (≥2 ГБ → HIGHLOAD); **none** — пропустить | AUTO — разумный выбор по умолчанию |
| 6. irqbalance | Распределение прерываний по ядрам CPU | Полезно на многоядерных серверах |

**Что ещё умеет модуль A:**

- **Пункт 8 главного меню — IPv6.** Отключение IPv6 (с бэкапом и скриптом отката `/root/restore-ipv6.sh`) или включение обратно. Отключение IPv6 рекомендуется для избежания утечек трафика.
- **Пункт 9 — Статус UFW.** Показывает действующую политику и правила без запуска сторонних инструментов.

**После завершения** скрипт покажет:
- Путь к бэкапам: `/root/remna-universal-backups/`
- Полный лог: `/var/log/remna-universal.log`
- Предложит перезагрузку, если она требуется

## 6. Модуль B: установка и управление нодой

### 6.1 Установка ноды (пункт 3 главного меню)

Скрипт проводит по этапам:

#### Перед установкой — UFW и доступ SSH

При первой установке ноды скрипт проверяет UFW до загрузки Xray и настройки Docker. Если UFW выключен, скрипт определяет серверный порт текущей SSH-сессии либо ищет единственный порт, который слушает SSH-сервер. Если порт определить не удалось, введите фактический порт вручную: скрипт проверит наличие TCP-слушателя. Если пакет UFW отсутствует, он устанавливается после проверки порта.

Скрипт добавляет и проверяет сохранённое разрешение для SSH, **и только затем включает UFW**. Он не меняет политику по умолчанию. При неподтверждённом SSH, нестандартной входящей политике или сохранённых ограничивающих правилах `deny`, `reject` либо `limit` автоматическое включение не выполняется. Если на VPS уже есть собственные правила nftables/iptables или UFW `before.rules`, проверяйте их через консоль провайдера. Не закрывайте текущую SSH-сессию до успешного входа во второй.

#### Этап 1 — Сетевая оптимизация и зависимости
Сетевой профиль применяется только при явном выборе **Y**; по умолчанию ядро не перенастраивается. Включайте профиль после замеров.

#### Этап 2 — Версия Xray-Core
При установке скрипт запрашивает текущий стабильный релиз Xray-Core через официальный endpoint GitHub `/releases/latest`, скачивает архив для архитектуры сервера и сверяет SHA‑256 по `.dgst` этого же релиза. Если GitHub недоступен или проверка не прошла, установка прекращается, а встроенная версия не подставляется. Для действующей ноды пункт 3 предлагает обновиться до последней стабильной либо указать точный тег вручную.

#### Этап 3 — Данные для связи с панелью

Скрипт по очереди спросит:

| Вопрос | Пример | Примечание |
|---|---|---|
| IP адрес панели Remnawave | `203.0.113.10` | IP **панели**, не этого сервера; используется для правил UFW |
| Домен ноды | `node.example.com` | A-запись должна смотреть на этот сервер |
| Порт управления нодой | `2222` (по умолчанию) | Порт, который панель использует для связи с нодой |
| **Сертификат ноды (secret key)** | длинная строка | Вставьте из панели; **завершите ввод двойным Enter** |

> ⚠️ Secret key выдаётся в панели Remnawave: Nodes → Create → скопируйте ключ. Если ввести пустой ключ — установка прервётся.

#### Этап 4 — Выбор конфигурации

```text
 1) VLESS-Reality (с выбором SNI)
 2) VLESS+TLS
 3) VLESS+xHTTP+TLS
 4) VLESS+TLS + VLESS+xHTTP+TLS + Hy2 одновременно
```

**Для VLESS-Reality** установщик сразу запросит SNI — полное DNS-имя без `https://`, порта, пути или wildcard, например `www.example.org`. Значения по умолчанию нет. Введите имя из `serverNames` Reality-inbound, а не адрес ноды; в клиенте должно использоваться это же имя как `serverName`. Установщик сохраняет SNI и подставляет его в `server_name` nginx, но не меняет inbound в панели. Для своего nginx в качестве TLS-цели убедитесь, что его сертификат покрывает выбранное имя: в режиме Reality установщик не выпускает публичный сертификат автоматически. Остальные режимы используют TLS-сертификат для домена ноды.

#### Этап 5 — Порты и выпуск сертификата

- В режимах **1–3** сохраняется прежнее поведение: порты 80 и 443 открываются автоматически, дополнительные порты задаются через пробел.
- В режиме **4** укажите порты активных inbound в порядке: **VLESS+TLS TCP**, **VLESS+xHTTP+TLS TCP или UDP**, **Hy2 UDP**. Для xHTTP поверх HTTP/3 укажите `порт/udp` (например, `1500/udp`); для xHTTP поверх HTTP/1.1 или HTTP/2 — `порт/tcp` или просто номер. Слушатели одного протокола TCP/UDP должны использовать разные порты; TCP и UDP могут использовать одинаковый номер. Не используйте порт управления и `61000`. UFW получает отдельные правила, без автоматического открытия 80 и 443. Исключение — standalone HTTP-01, которому нужен TCP/80 для выпуска и продления.
- Одна нода Remnawave использует [один Config Profile](https://docs.rw/learn-en/nodes/). Если протоколы сейчас в трёх отдельных Config Profiles, создайте один профиль с тремя inbound и активируйте их на нужной ноде. Установщик не создаёт и не переключает профили. Сгенерированный для нового деплоя nginx принимает обычный HTTP на Unix-сокете за Xray; режим не предназначен для автоматической миграции собственного nginx с TLS на сокете.

**Для TLS/xHTTP/Hy2** установщик предложит выпуск сертификата:

```
🔐 ВЫБОР МЕТОДА ВЫПУСКА SSL СЕРТИФИКАТА
 1) Cloudflare API (DNS-01, wildcard *.домен)
 2) Certbot Standalone (HTTP-01, по 80 порту — стандартно)
 3) Gcore DNS API (DNS-01, wildcard *.домен)
```

| Метод | Что нужно | Когда использовать |
|---|---|---|
| Cloudflare API | API Token + домен на Cloudflare | Автообновление, wildcard |
| Standalone | Только email + открытый порт 80 | Проще всего, домен на любом DNS |
| Gcore API | API Token + домен на Gcore | Автообновление, wildcard |

Для DNS-01 по умолчанию выпускается сертификат на точное имя; для wildcard укажите делегированную зону. Wildcard покрывает только один уровень: при зоне `example.com` запрос для `node.example.com` содержит `example.com` и `*.example.com`, а более глубокие имена добавляются отдельно. Для Gcore заранее установите совместимый плагин. Standalone прекращает работу при занятом TCP/80, не останавливая сервисы. В режиме 4 он также недоступен, если TCP/80 назначен одному из VLESS inbound; для этого случая используйте DNS-01. Deploy-hook реагирует только на активный сертификат ноды.

#### Этап 6 — Деплой и файрвол
- Генерируется `docker-compose.yml`: контейнеры **remnanode** + **remnawave-nginx** (маскировочный сайт)
- Встроенный шаблонизатор создаёт статическую страницу в `/opt/remnanode/www` (три темы, ручной или случайный выбор)
- Правила ноды добавляются в уже активный UFW без изменения системной политики. Проверьте существующие разрешения на порт управления.

### 6.2 Меню управления нодой (пункт 5 главного меню / команда `remnanode`)

```
📌 Текущий статус ноды: Активна (Запущена)
 1) 🚀 Первоначальная настройка и запуск ноды
 2) 🔐 Выпуск и обновление SSL при смене домена ноды
 3) ⚡ Установка/Обновление кастомной версии Xray-Core
 4) 🔌 Смена IP адреса панели (Обновление правил UFW)
 5) 🔌 Управление клиентскими портами Xray и UFW
 6) 🎭 Настроить HTML-шаблон
 7) 📊 Диагностика и просмотр логов ноды
 8) 🗑️  Удаление ноды без сброса UFW
 0) Назад
```

#### Пункт 2 — Смена домена ноды и SSL
- Вводите новый домен
- Для TLS/xHTTP перевыпускает SSL (выбор метода заново)
- Перезапускает контейнеры с новым доменом

#### Пункт 3 — Обновление Xray-Core
- Заново показывает список версий с GitHub
- Скачивает и проверяет выбранную версию, затем обновляет Compose

#### Пункт 4 — Смена IP панели
- Показывает текущий разрешённый IP
- Вводите новый — скрипт добавит новое правило UFW и только затем удалит старое

#### Пункт 5 — Управление клиентскими портами
```
 1) ➕ Добавить новый клиентский порт / диапазон портов Xray в UFW
 2) ➖ Удалить порт / диапазон из списка разрешенных
 3) 🔄 Принудительно перезагрузить правила брандмауэра (UFW reload)
```
- Можно добавить одиночный порт (`8443`) или диапазон (`2000:2010`)

#### Пункт 6 — Настроить HTML-шаблон
Выберите «Статус», «Минимализм», «Тёмная» или случайную тему. Заменяется только `/opt/remnanode/www/index.html`, без перезапуска nginx. Старый общий webroot не изменяется. Для добавления скина расширьте каталог в `rn_render_page_template` и `rn_pick_page_template`.

#### Пункт 7 — Диагностика и логи
Nginx пишет `access.log` и `error.log` в `/var/log/nginx` на хосте. Если найден отдельный системный `/etc/logrotate.d/nginx`, контейнер пишет в `/var/log/remnanode/nginx`, чтобы не делить журналы и правила ротации с системным nginx.

Для файловых логов Xray добавьте/обновите объект `log` в конфигурационном профиле панели Remnawave. Монтаж каталога сам по себе не включает логирование трафика:

```json
{
  "log": {
    "access": "/var/log/remnanode/access.log",
    "error": "/var/log/remnanode/error.log",
    "loglevel": "warning"
  }
}
```

Журнал процесса Xray (`s6`) доступен в `/var/log/remnanode/xray/current`; сам s6 управляет этим файлом, отдельная ротация для него не назначается. Вывод приложения `remnanode` доступен через `docker logs remnanode` с ограничением 20 МБ × 5 файлов. Файлы `access.log` и `error.log` для Xray и nginx ротируются системным logrotate: ежедневно, либо по `maxsize 50M` при очередной проверке, 7 архивов. Для nginx после ротации используется сигнал `USR1`, а не перезапуск.

Показывает:
- Ресурсы сервера (CPU, RAM, диск)
- Статус контейнеров (remnanode, remnawave-nginx)
- Размеры логов

И позволяет:
```
 1) 📥 Лог запросов Xray (access.log) в реальном времени
 2) 📥 Лог ошибок Xray (error.log) в реальном времени
 3) 📥 Лог запросов веб-сервера Nginx в реальном времени
 4) 📥 Вывод логов из контейнера Docker (remnanode)
 5) 🔄 Вынужденно применить ротацию логов (logrotate)
```
> 💡 Выход из просмотра логов — **Ctrl+C** (прерывается только просмотр, меню остаётся).

#### Пункт 8 — Удаление ноды
Останавливает Compose и удаляет файлы ноды, отдельный webroot и собственный hook. Логи на хосте сохраняются. Сохраняет образы, оригиналы сертификатов Certbot, общий webroot, UFW, sysctl и сторонние hook. Если остановить контейнеры не удалось, файлы остаются на месте. Оставшиеся правила UFW и старые настройки проверьте вручную.

## 7. Модуль C: защита RKN Watcher 3.2.1

### Установка или обновление кода (пункт 4)

```bash
bash ./safe-remnanode-setup.sh protect-version
sudo bash ./safe-remnanode-setup.sh protect
sudo rkn-watcher --version
sudo rkn-watcher doctor
```

Первая команда показывает **встроенную** версию, третья — **установленную**. Однофайловый установщик извлекает встроенный комплект; при модульном запуске комплект берётся из `vendor/rkn-watcher/`. В обоих случаях скрипт проверяет целостность и разворачивает программу в `/opt/rkn-watcher/`, включая `lib/`, `config_tool.py` и `geoip_apply.py`. Установка проверяет зависимости и доступность правил nftables; интеграция не предлагает запускать `nftables.service`. При обновлении сохраняются прежние настройки, а перед заменой файлов создаётся копия в `/var/backups/safe-rkn-watcher.*/files.tgz`. После установки штатный RKN Watcher обновляет списки и применяет правила — выполняйте это через консоль VPS или при доступе к ней, особенно при включённом GeoIP.

### Управление защитой (пункт 6)

```bash
sudo rkn-watcher                    # меню
sudo rkn-watcher status --json      # статус в JSON
sudo rkn-watcher update             # обновление списков, не версии программы
sudo rkn-watcher apply --dry-run    # диагностическая проверка без изменения firewall
sudo rkn-watcher snapshots          # имеющиеся снимки
sudo rkn-watcher metrics            # метрики
```

Для allow/deny IP и CIDR можно использовать IPv4 и IPv6 при наличии `ip6tables` и поддержки ядром. `doctor` показывает настроенный и фактический netfilter-бэкенд. Не переключайте его поверх работающего UFW без проверки. При `PORT_POLICY=strict` порты вне `FILTER_PORTS` блокируются: заранее проверьте SSH, порт управления панели и клиентские порты. Снимок `rollback` может восстанавливать таблицы firewall целиком, не запускайте его на рабочем сервере без просмотра снимка и доступа к консоли.

Для удаления программы используйте `sudo rkn-watcher uninstall`. Это удаление защиты и её конфигурации; пакеты на хосте через эту команду не удаляются. См. также [руководство RKN Watcher](https://github.com/Balbuto/RKN-Watcher/blob/3c88c27a65181a93921a21b2d8a28f2292df1e03/docs/ru/USAGE.md).

## 12. Безопасность и рекомендации

### Что скрипт делает для безопасности
- **Порт управления нодой** (2222) открыт в UFW **только для IP панели**
- UFW по умолчанию: `deny incoming` / `allow outgoing`
- SSH-порт определяется автоматически и не блокируется (защита от локаута)
- Все внешние скрипты качаются только по HTTPS
- Бэкапы всех изменяемых файлов перед правкой
- Secret key хранится в `.env` с правами 600 (только root)
- Повторная установка ноды требует подтверждения (чтобы не потерять ключ)

### Рекомендации после установки
1. **Смените SSH-порт** и включите вход по ключам (с учётом действующей политики firewall)
2. **Проверьте статус защиты** через `sudo rkn-watcher status` — счётчики списков должны быть ненулевыми
3. **Проверьте ноду в панели** Remnawave: статус должен стать «активна»
4. **Настройте мониторинг** панели (Remnawave умеет слать алерты о недоступности ноды)
5. Периодически запускайте `sudo safe-remnanode-setup multitest` для базовой диагностики
6. Следите за обновлениями: `sudo remnanode` → пункт 3 (Xray), обновления панели — через панель

### Чего делать не стоит
- Не открывайте порт управления нодой для всех (правило UFW «только для IP панели» — это защита от атак)
- Не отключайте UFW без необходимости
- При полном удалении ноды помните: UFW сохраняется, лишние правила нужно снять вручную

## 13. Частые вопросы и решение проблем

### ❓ Скрипт не запускается: «Должен быть запущен от имени root»
Запускайте с sudo: `sudo ./safe-remnanode-setup.sh`

### ❓ При установке защиты: «Ядро не поддерживает ipset»
Модуль xt_set отсутствует в ядре (часто в контейнерах/OpenVZ). Защита не сможет применять правила. На VPS/KVM-серверах обычно работает.

### ❓ Нода установлена, но в панели статус «неактивна»
1. Проверьте, что в панели указан **правильный IP и порт управления** (по умолчанию 2222)
2. Проверьте, что secret key совпадает
3. `sudo remnanode` → пункт 7 → убедитесь, что контейнер `remnanode` запущен
4. Проверьте UFW: порт управления должен быть разрешён **только с IP панели**

### ❓ Клиенты не подключаются
1. `sudo remnanode` → пункт 7 → посмотрите логи Xray (пункт 1/2)
2. Проверьте, что порт клиента открыт: `sudo ufw status`
3. Добавьте порт: `sudo remnanode` → пункт 5 → пункт 1
4. Проверьте Censorcheck DPI — возможно, провайдер режет протокол

### ❓ SSL не выпускается (Standalone): «Порт 80 занят»
Скрипт сам останавливает nginx/контейнеры перед выпуском и ждёт освобождения порта. Если не помогло — проверьте, что на 80 порту не висит другой сервис: `ss -tlnp | grep :80`

### ❓ После ребута пропали правила защиты
Должен сработать `rkn-watcher-boot.service`. Проверьте:
```bash
systemctl status rkn-watcher-boot.service
```

### ❓ Хочу отключить автообновление списков
`sudo rkn-watcher` → пункт 3 (Настройки) → пункт 3 (AUTO_UPDATE) → нет

### ❓ Как посмотреть, что делал скрипт?
```bash
tail -f /var/log/remna-universal.log      # общий лог
tail -f /var/log/rkn-watcher/update.log   # обновления списков
tail -F /var/log/remnanode/error.log  # ошибки Xray
```

### ❓ Скрипт обновился — как получить новую версию?
```bash
sudo bash ./safe-remnanode-setup.sh install-cli
```
